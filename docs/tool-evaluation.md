# 電商決策場景的工具對照

這份記錄對應 2026-10-21 提出的一批候選工具。它們補的是電商決策場景的具體缺口，不是另一批通用 OSINT 套件。

此處只做層級對照和取捨。沒有把它們加進依賴，也沒有改採集行為。已落地的能力仍以 `docs/decisions.md` 的代碼對照為準。

## 不採納的能力

下列能力與既有結論衝突，候選工具裡即使帶有這些模組，也不接入稜鏡：

- 驗證碼、登入牆、付費牆的繞過，以及瀏覽器指紋模擬。
- 登入態價格、Cookie 庫、帳號會話複用。
- 目標拒絕、驗證碼或頻率限制之後換 IP 再試。
- 帳號枚舉、郵箱註冊探測、暗網或洩漏庫檢索。
- 模型產出或修復出貨幣金額。
- 把優惠求解放進 `prism/weave/`。場景計算留在 `prism/commerce/`。
- 用全局窮舉打亂固定優惠順序。順序仍是單品級、店鋪級、平台級、紅包、國補。國補用前面抵扣後的實付價，不能改回原標價。

公開頁面上的 sitemap 或 JSON-LD，只有在網域已允許、路徑未命中禁止片段、且 robots 允許時，才可以成為日後的輕量通道。它不能在瀏覽器路徑被拒絕之後當作繞過。

## 按層對照

| 中國平台商品頁採集 | SuperSpider | L1 探針 | 電商頁沒有站點預設；商品圖只抓允許網域上標成商品圖的公開檔 | 路由形態可參考。反爬、Cookie、指紋與站點登入預設不接入 |
| 可審計的採集產物 | Tentacrawl | L2 採集 | 原始位元組進物件庫，鍵為 `raw_ref` | 可參考 Markdown、JSON、HTML 快照、截圖並存。challenger 不接入 |
| 登入態與團隊報表隔離 | ecom-competitor-monitor | L1 合規邊界 | 登入態探針未啟用；登入態標價有金額時拒絕入庫 | 只保留「帳密不進團隊可讀面」這個隔離想法。不實作淘寶登入採集 |
| 低干擾的公開價格路徑 | price-monitoring-free | L1 後備通道 | 沒有 sitemap 或 JSON-LD 讀取器 | 可作為日後的公開頁後備。被風控後不得自動改走這條 |

| 自托管價格追蹤 | Discount-Bandit、pricebuddy、ecommerce-price-watcher | L3 通知參考 | 告警走號角，目前乾跑 | 不嵌入。SSRF 防護的寫法可參考，不因此擴大採集範圍 |
| 調價建議骨架 | price-monitor | L4 研判參考 | 排序是可配置加權和，不輸出絕對最低價 | 不採用「降到競品價的某個比例」這種新標價。模型仍不得寫金額 |
| 優惠表達式與中間值追溯 | QLExpress | L3 場景計算 | `AppliedStep` 已記錄每層的基數、抵扣與抵扣後實付 | 追溯形態已有。不引入 Java 腳本引擎 |
| 平行優惠、互斥、剪枝 | QYDiscount | L3 場景計算 | `prism/commerce/rules.py` 按固定順序求解，同層互斥取優先級 | 只吸收分層、互斥和剪枝的問題建模。不換成全局最優窮舉，也不搬進 `weave/` |
| 促銷規則 DSL | promotion_kit | L3 參考 | 調整項已有種類、數值、互斥組、優先級、有效期、資格 | 不引入 Rust 套件 |
| 券狀態與審核流 | Qpon | L3 持久化參考 | 資格不明的層不套用，並寫入不確定項 | 不引入 NestJS 券平台 |
| 流式結構校驗與分層修復 | fluxmend | L4 引用、L5 簡報 | `prism/llm/validate.py` 解析失敗重試一次；未知引用標 `unsupported`；閘道拒絕貨幣金額 | 日後可評估語法修復。不得把 unsupported 引用或金額修成可採用值 |

| 工具目錄 | awesome-osint-repos、awesome-osint-arsenal | 閱讀索引 | 無 | 可以當書目。一鍵安裝器不進本倉庫 |

## 和現有程式的對應

電商計算不在歸併核心。

- 探針路由的首選與備選在 `prism/raven/router.py`。全部失敗必須顯式降級。
- 劣化速率提前走備選在 `prism/raven/degrade.py`。這是 World Monitor 的來源組新鮮度沒有覆蓋、已經自建的部分。
- 出口代理池在 `prism/raven/proxies.py`，預設關閉。只在傳輸失敗時換路。
- 站點規則在 `prism/raven/compliance.py`，未登記網域預設拒絕。
- 商品圖在 `prism/raven/images.py`。普通圖片、廣告、登入與驗證碼路徑不抓。
- 優惠順序、互斥和國補基數在 `prism/commerce/rules.py`。
- 價格中位數在 `prism/commerce/baseline.py`，不寫入 `event_metrics`。
- 排序、價保布爾和分級棄權在 `prism/commerce/decide.py`。
- 貨幣金額拒絕在 `prism/llm/money.py`。引用是否落在已知提及上，由 `prism/llm/validate.py` 標成 unsupported，不自動改寫。

## 建議寫進規則層、但不搬位置的建模

QYDiscount 把券分成訂單、跨店、店鋪、商品、分類、組合、運費、支付等層，再在互斥條件下剪枝。稜鏡已有的層是單品、店鋪、平台、紅包、國補。對照時沿用這五層，不另起一套會改寫順序的分類。

可以吸收的只有三點，而且都落在 `prism/commerce/rules.py`：

1. 同一層的互斥要先偵測，再決定哪一張券生效。現在同 `exclusive_group` 取較高優先級，平手取較大優惠。
2. 剪枝只能刪掉已證明不可能更優、且不違反固定順序的組合。不能為了更低的實付把國補提前，也不能套用資格不明的層。
3. 算錯時要能指出哪一層的基數和預期不一致。現有步驟已保存 `base_before`。全局只吐一個實付數字不夠。

不吸收的是「窮舉出全局最優」。那會把固定順序變成可重排的搜尋，直接違反國補最後、錯誤順序必須拒絕的結論。QYDiscount 自己標成未經生產檢驗的測試方案，因此不列為依賴。

QLExpress 的表達式追蹤和上面第 3 點是同一件事，不另引引擎。

## 日後小樣本要先寫停損

SuperSpider、QYDiscount、fluxmend 值得用公開、小樣本的方式核對，而不是先接進主路徑。核對時的停損如下：

- SuperSpider：只許對已允許網域的公開頁看站點預設能否抽出標價與商品圖。一旦需要登入、Cookie、指紋、驗證碼或拒絕後換 IP，這次核對結束，不記成「通道可用」。
- QYDiscount：只用已寫明的券規則核對剪枝會不會漏掉固定順序下的合法組合，或偷偷套用國補到原標價。不拿它的最優解覆蓋 `solve()`。
- fluxmend：只許修復括號和逗號這類語法。引用 ID 經編輯距離改寫、字串數字被改成數值、金額被修復後保留，都算失敗。應維持 unsupported 或直接拒絕的欄位，不能被修成可採用。

price-monitoring-free 的 sitemap 與 JSON-LD 若要核對，使用同一套停損：網域未允許、robots 不允許，或這次請求是因為前一條通道被拒絕而改走，都不算後備成功。
